    01What it catches

    The signatures an agent should never send.

    Each of these is a real check, read from the intent and then from the exact calldata. The verdict word is the one the instrument above would show, on the same published scale.

    Block

    An unlimited approval

    An approve for the maximum uint256 hands a spender the entire balance, indefinitely. SafeHands reads the amount in the calldata and blocks the unbounded grant.

    Warn

    A brand-new recipient

    A transfer to a wallet with no history on chain 1672. It could be correct, or an address-poisoning lookalike a character off. Flagged for a second look.

    Warn

    An unverified spender

    A router or contract with no first-party registry evidence. Recognition needs proof, so an unknown counterparty never clears on its own.

    Warn

    A price it cannot trust

    A Chainlink feed that is stale or missing. SafeHands reports it and refuses to quote it: a price it did not read live is never guessed.

    Block

    A contract that changed under you

    A verified address whose live bytecode no longer matches what was recorded. SafeHands catches the silent swap by code hash and stops.

    Block

    A transfer that will revert

    A permissioned real-world-asset leg where the wallet is not eligible or the token is frozen. SafeHands checks before you sign, not after it fails.

    02How it works

    Four steps, and only one of them is ours.

    STEP 01

    The agent plans

    Your model finds the opportunity and builds the transaction. It holds the intent, never a key.

    STEP 02

    The engine reads

    SafeHands checks the intent, then the exact calldata, against the on-chain registry and live evidence.

    STEP 03

    A verdict, not a vibe

    One score on a published scale, with named reasons. Same bytes in, same verdict out.

    STEP 04

    Your wallet acts

    Only what cleared reaches a signature. SafeHands never touches a key.

    A firewall that cannot move funds is one nobody has to trust with funds. That is the whole design: safety you can put in front of an agent without handing anything over.

    03Why trust it

    Five properties, each one checkable.

    Deterministic

    Every verdict is computed by code and traces to a named check. Run it twice on the same bytes and you get the same answer, with the same reasons.

    Registry-backed trust

    Recognition comes only from first-party, on-chain registry evidence. Being listed somewhere is not trust, and a contract recognized by name is still not a contract approved to spend.

    Fail-closed

    Missing evidence is reported as unknown and pushes the verdict up. Aggregation can only raise severity. A block is never downgraded by anything downstream.

    Zero-custody

    Read-only by design. No keys, no signing, no broadcasting on the hosted surface. Write paths exist for self-hosting, off by default behind explicit gates.

    Live on mainnet

    Running against Pharos Pacific Mainnet, chain 1672, with live Chainlink prices and risk records committed on-chain and proven against the published Merkle root.

    And what it never does.

    [X]

    Never holds a private key, and never signs or broadcasts on the hosted surface.

    [X]

    Never quotes a price it did not read live from Chainlink. A stale feed is reported, never guessed.

    [X]

    Never grants trust from anywhere but the registry's first-party evidence.

    [X]

    Never downgrades a block. Aggregation can only raise severity, never lower it.

    A verdict binds to exactly what was inspected. Act on different bytes, or after it expires, and it no longer applies. The calling agent is expected to check that binding, not to assume it.
